# Updating or Fixing an Existing Article

Found a typo, outdated command, or missing information? This guide shows you how to submit a fix. All edits go through a Pull Request so an admin can review them before they go live.

<Callout type="info">
  Every NexDocs page has an **"Edit this page"** link at the bottom. Clicking it opens the file directly in GitHub's web editor — the fastest path for small fixes.
</Callout>

---

## Before you start

You will need:

- A **GitHub account**
- Write access to [EyecomDesign/nexdocs](https://github.com/EyecomDesign/nexdocs) (ask an admin if you don't have it)

---

## Option A — Quick fix via GitHub web editor (recommended for small edits)

Best for: typos, wording, broken links, or any change that touches one file.

<Steps>

### Find the page on the live docs

Navigate to the page you want to fix at `localhost:3000` (dev) or the live site at `docs.nexor.app`.

### Click "Edit this page"

Scroll to the bottom of the page and click the **Edit this page** link. This opens the raw MDX file on GitHub.com.

<Callout type="warning">
  If you don't see the link, the page may be marked as non-editable or you may not be logged into GitHub.
</Callout>

### Make your changes in the web editor

GitHub opens an in-browser editor. Make your edits directly in the file.

<Callout type="tip">
  Click the **Preview** tab in the GitHub editor to see a rough render of the Markdown before you save.
</Callout>

### Commit to a new branch

Scroll down to **Commit changes**:

1. Write a short commit message — e.g. `fix: correct command flag in getting-started`
2. Select **"Create a new branch for this commit and start a pull request"**
3. Name the branch something like `fix/getting-started-typo`
4. Click **Propose changes**

### Open the Pull Request

GitHub will take you straight to the **Open a pull request** page. Add a title and a brief description of what you fixed, then click **Create pull request**.

<Callout type="info">
  An admin will review your PR at [/admin/prs](/admin/prs). Once approved and merged, the fix goes live immediately.
</Callout>

</Steps>

## Option B — Edit locally (recommended for larger changes)

Best for: restructuring sections, updating multiple files, or adding code examples.

<Steps>

### Find the source file

All content lives in the `content/` folder of the repository. The URL maps directly to the file path:

| Page URL | File path |
|---|---|
| `/guides/getting-started` | `content/guides/getting-started.mdx` |
| `/api-reference/overview` | `content/api-reference/overview.mdx` |

### Create a new branch

```bash
git checkout master
git pull
git checkout -b fix/short-description-of-fix
```

<Callout type="warning">
  Never commit directly to `master`. Your branch name should briefly describe what you're fixing, e.g. `fix/broken-rsync-command` or `docs/update-prerequisites`.
</Callout>

### Open and edit the file

Open the `.mdx` file in your editor. The content is standard Markdown — you can edit it like any text file.

**Common things to fix:**

| Issue | What to change |
|---|---|
| Wrong command or flag | Update the code block |
| Outdated version number | Find and replace the old version |
| Missing step | Add a new `###` section in the right place |
| Broken link | Update the `[text](url)` or internal path |
| Typo / grammar | Edit the text directly |

<Callout type="error">
  Do **not** change the `title` or `description` in the frontmatter unless you intend to rename the page. Changing `title` affects the browser tab and search results.
</Callout>

### Check the sidebar label (if you renamed anything)

If you renamed a file or changed its frontmatter `title`, also update the matching entry in the section's `_meta.ts`:

```ts
// content/guides/_meta.ts
export default {
  "getting-started": "Getting Started",  // ← sidebar label lives here
}
```

The sidebar label and the frontmatter `title` can differ — keep the sidebar label short.

### Commit and push

```bash
git add content/guides/the-file-you-edited.mdx
git commit -m "fix: describe what you fixed in one line"
git push -u origin fix/short-description-of-fix
```

### Open a Pull Request

Go to the repository on GitHub. Click **Compare & pull request** on the banner for your branch.

Fill in:
- **Title** — e.g. `fix: update rsync path in TrinityCore guide`
- **Description** — what was wrong and what you changed

Then click **Create pull request**.

<Callout type="info">
  An admin will review your PR on GitHub and merge or request changes. You'll get a GitHub notification when it's reviewed.
</Callout>

</Steps>

---

## What happens after you submit

1. Your PR shows up on GitHub for review
2. An admin reviews the changed files and either **merges** or **closes** the PR
3. If merged into `master`, Cloudflare Workers Builds automatically redeploys the docs site
4. If closed with feedback, update your branch and the PR will refresh automatically

---

## Checklist before submitting

- [ ] Only changed what needed fixing — no unrelated edits in the same PR
- [ ] Code blocks still have the correct language hint (` ```bash `, ` ```ts `, etc.)
- [ ] Links still work (internal paths start with `/`)
- [ ] Commit message is descriptive (`fix: ...` or `docs: ...`)

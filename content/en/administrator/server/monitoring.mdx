# 📊 Monitoring

Monitoring helps an authorized operator determine whether an incident concerns
availability, request processing, capacity or data. Request dashboard access using
the [Access](/en/administrator/server/access) procedure.

## Start with one reproducible symptom

Record the time and time zone, affected service or public route, bot revision,
game flavor and map. State the expected result and the actual response. Use a
small reproducible case rather than posting a full unsanitized session log.

An unreachable endpoint, a rejected request and a valid response with no usable
route are different observations. Preserve that distinction when reporting the
problem.

## Useful observations

| Signal | What to investigate |
| --- | --- |
| Availability and returned status | Service reachability, request failures and whether a dependency is unavailable. |
| Request latency and volume | Slow processing, increased demand or a change after a release. |
| Worker capacity and queued work | Whether work is waiting or workers are failing. |
| CPU, memory and disk | Resource pressure, storage growth and available headroom. |
| Map or dataset coverage | Whether the requested flavor and map have the intended data. |
| Client and service revision | Whether the observation corresponds to the version under investigation. |

Use the actual metric names, thresholds and resource limits in the current
deployment's private runbook. Historical capacity numbers do not establish a
current operating limit or scaling trigger.

## When metrics are missing

1. Check the affected service's health separately from the dashboard.
2. Check that the observation covers the correct environment and time window.
3. Ask an operator to verify the metrics collector, target configuration and
   relevant network access.
4. Compare the last working release and recent configuration changes.

A blank dashboard alone does not prove that pathfinding is down. Conversely, an
available dashboard does not prove that customer requests work.

## Documentation-site checks

For the docs site, record the HTTP response and deployed revision for a real
Introduction, Developer and Administrator page. Check the health endpoint and
search resources separately. A working search script alone does not prove that
pages render successfully.

Share only sanitized results. Credentials, cookies, private dashboard addresses
and deployment inventory belong in the private operator record. See
[Deployment](/en/administrator/server/deployment) for release verification and
[Operations](/en/administrator/server/operations) for maintenance.

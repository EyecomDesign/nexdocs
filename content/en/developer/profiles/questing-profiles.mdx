# Questing Profiles

A questing profile describes one quest: its start, objectives and turn-in. Load
it in **Profiles** and start the bot to run the whole file, or use a
[task routine](/en/developer/tasks/task-routines) for a whole quest or one phase
at a time. A directly loaded quest stops the bot when no phase remains.

These contracts follow the current
[quest handler](https://github.com/NexorSystem/NexorBot/blob/9f373eaa9bd3d65581fc5ad6c52a417b87c71a89/src/machines/profiles/questing.lua)
and [Profile Tool exporter](https://github.com/NexorSystem/NexorBot/blob/9f373eaa9bd3d65581fc5ad6c52a417b87c71a89/UI/Frames/BotInterface/ProfileTool/ProfileTool.lua).
Quest IDs, objectives and NPCs can differ by game flavor and server. Check them
on the character that will run the profile.

## A complete file

This author-owned **Retail / Valley of Trials** example follows quest 25126,
*Cutting Teeth*. It requires the preceding quest to have made Gornek's offer
available. Save it as
`Nexor_User/Profiles/MyProfiles/Retail/25126_Cutting_Teeth.lua`; this example is
not a promise that the file ships as a default product.

```lua
local NX = ...

local Profile = {
    Name = "Cutting_Teeth",
    Type = "QUESTING",
    NPCs = {},
    Executecodeorder = {
        questid = 25126,
        PickUp = {
            npcid = 3143,
            Points = { { -597.74, -4248.26, 38.96, 5, MapID = 1 } },
        },
        Objectives = {
            {
                type = "KillAndLoot",
                objectiveIndex = 1,
                WhitelistIDs = { 3098 },
                Points = {
                    { -471.28, -4270.47, 42.89, 35, MapID = 1 },
                    { -433.26, -4287.73, 42.86, 35, MapID = 1 },
                    { -494.11, -4340.77, 38.66, 35, MapID = 1 },
                },
            },
        },
        TurnIn = {
            npcid = 3143,
            Points = { { -597.74, -4248.26, 38.96, 5, MapID = 1 } },
        },
    },
}

return Profile
```

The loader accepts a Lua chunk returning a table, as above, and legacy
`Profile = { ... }` files. `Executecodeorder` selects the quest runner; normal
grinding profiles use top-level `Points` instead. Keep the exact field names.
Handwritten scripts can have local helpers; the Profile Tool only reopens its
marked, round-trip-safe script files.

Load the local file in **Profiles**, check its name, then start. The active phase
should change from `PickUp` to `KillAndLoot`, then `TurnIn`. The quest must enter
the log, objective 1 must gain credit, and the quest must leave the log after
turn-in. If those observations fail, stop and check the offer, IDs, objective
order and destination map. Use the bot's Stop control to interrupt a run.

## Phase order and completion

`Executecodeorder.questid` is the server's quest ID. `PickUp` and `TurnIn` are
optional top-level blocks. `Objectives` runs in **array order**;
`objectiveIndex` identifies the corresponding 1-based quest-log objective,
not the execution order. Already accepted, credited or turned-in work is skipped
from live quest state.

In the table, **objective credit** means the specified `objectiveIndex` is
finished. Without an index, ordinary objective phases wait for all objectives.
A quest already turned in completes every phase. A successful item use, spell
cast or interaction alone does not prove objective credit.

| Phase | Required authored inputs | Completion and material limits |
| --- | --- | --- |
| `PickUp` | Top-level block with `npcid` and search `Points`, or the item offer below | Quest enters the log, or was already turned in. QuestTalk approaches a live NPC; multiple points search for a moving giver, while one point waits there if the NPC is absent. |
| `TurnIn` | Top-level block with `npcid` and `Points` | Quest is turned in, not merely ready to hand in. Requires a valid offer/reward interaction. |
| `CompleteQuest` | Top-level `CompleteQuest = { npcid = ..., Points = ... }`, selected by `Run Quest Phase` | Same NPC hand-off/completion as `TurnIn`. Full runs select `TurnIn`; use that name there. A `CompleteQuest` row exported inside `Objectives` is not the top-level block the phase resolver expects. |
| `KillAndLoot` | `objectiveIndex`, intended mob `WhitelistIDs`, search `Points` | Objective credit. Uses normal engage/loot handling. These IDs enable quest-target eligibility, including the trivial-target exception; the current combat scanner does not enforce them as an exclusive ID filter. Other eligible enemies and self-defense can still be handled. |
| `Grinding` | Search `Points`; optional mob `WhitelistIDs` | Kill/loot behavior, but no objective-based completion. Ends only when the whole quest is turned in or its routine stops it. Prefer `KillAndLoot` for an objective. |
| `Gathering` | Node/object `WhitelistIDs` or `objectid`, search `Points`, `objectiveIndex` | Objective credit. Reuses object interaction; requires the skill/tool and loot access. |
| `InteractWithObject` | `objectid` or object `WhitelistIDs`, search `Points`, `objectiveIndex` | Objective credit. Scans GameObjects, approaches a matching object, interacts and waits through casting/channeling. No configurable gossip sequence. |
| `UseItemOnMob` | `itemid`, `npcid` or mob `WhitelistIDs`, search `Points`, `objectiveIndex` | Objective credit. Approaches an eligible unit to below 5 yards, settles targeting/movement and uses the item. Cast/channel and success observation prevent immediate repeated attempts; a successful attempt alone does not finish the phase. |
| `UseSpellOnMob` | `spellid`, `npcid` or mob `WhitelistIDs`, search `Points`, `objectiveIndex` | Objective credit. Approaches and casts on the selected unit (8-yard approach boundary); requires a known, suitable spell. |
| `UseItemOnSelf` | `itemid`, `objectiveIndex`; optional first point | Objective credit. Uses the item on `player`, optionally after approaching the point. |
| `UseSpellOnSelf` | `spellid`, `objectiveIndex`; optional first point | Objective credit. Casts on `player`, optionally after approaching the point. |
| `UseItemOnPosition` | `itemid`, first point, `objectiveIndex` | Objective credit. Walks to the point, then uses the item **on the player**. Does not place an item's ground-target reticle. |
| `UseSpellOnPosition` | `spellid`, first point, `objectiveIndex` | Objective credit. Approaches, casts, then clicks that world position if a ground reticle appears. Requires a suitable spell and world-click support. |
| `TalkTo` / `InteractWithUnit` | `npcid` or mob `WhitelistIDs`, search `Points`, `objectiveIndex` | Objective credit. Approaches/interacts with a matching unit. Does not implement a configurable gossip conversation tree. |
| `MoveTo` | First point with arrival radius and destination `MapID` | Arrival within that radius **on that map**. Ignores later points; needs no quest credit. No point leaves it blocked. |
| `CustomCode` | `customcode = function(NX, phase, substate) ... end` | In full runs: returns exactly `true`, or its real quest objective completes. Missing code warns and marks this standalone phase done. The single-phase task has the separate behavior below. |

The normal self/position/spell/interaction handlers allow a three-second grace
between attempts while waiting for server credit. They cannot make an
unsuitable item or spell usable. Self/position approach helpers act in the
current world; use `MoveTo` with `MapID` for a required world transition before
a local item/spell action.

## Points, IDs and target policy

The export shape is
`{ x, y, z, radius, MapID = mapID, Type = "Checkpoint" }`. These are world
coordinates, not the map UI's 0–100 percentages. `MapID` is the world/instance
map used by navigation, not a zone's UI map ID. Zero is valid. A legacy point
without a map uses the current-map fallback; preserve captured values for
cross-world travel.

The phase loader also accepts keyed `{ X, Y, Z, Range, MapID }` points. Prefer
the exporter's tuple shape in handwritten quests: item/spell position handlers
read numeric entries. Missing phase radii become radius 5 navigation points;
`MoveTo`'s own arrival test defaults to 3 if no radius was authored. Set an
explicit radius to make both behaviors clear.

Each phase defaults to **`Spot`**. Combat works from the selected point and its
radius. Set `Logic = "Path"` to patrol and scan around the player, or
`Logic = "Bounce"` for a route traversed back and forth with point-based combat.
`logic` is accepted as an alias; export writes `Logic`. Invalid overrides warn
and fall back to `Spot`.

| Field | Meaning |
| --- | --- |
| `questid` | Quest identity, normally on `Executecodeorder`; a phase may override it. |
| `objectiveIndex` | Actual 1-based quest-log objective for this flavor/server. |
| `npcid` | Creature/NPC ID for a giver or target unit. |
| `WhitelistIDs` | Creature IDs for combat/unit phases, GameObject IDs for object/gathering phases. These are different ID kinds. |
| `itemid` / `spellid` | Item to use or spell to cast. Spell phases accept the older shared `itemid` as fallback. The UI's **Item/Spell ID** exports as `spellid` for `UseSpell*`. |
| `objectid` | GameObject ID, such as a chest. The editor's **Object ID** exports here. |
| `targetState` | `"Any"` (default), `"Alive"` or `"Dead"` for `UseItemOnMob`, `UseSpellOnMob`, `TalkTo` and `InteractWithUnit`. Case is normalized; invalid values warn/use `Any`. |

A corpse interaction needs `targetState = "Dead"` and the correct unit ID.
Setting it on `KillAndLoot` does not change that phase's combat policy. Targeted
actions support friendly/neutral quest units; player-controlled units are
excluded.

## Item-started quests

In **Quest Steps → PickUp → Quest Start**, choose the item offer and enter the
starter item ID. If it is already in the bags, the runtime uses it and accepts
the matching quest. Otherwise, `acquire` rows describe how to obtain it, in
order. Supported methods: `KillAndLoot`, `InteractWithObject`,
`InteractWithUnit`.

This pickup shape comes from the item-start regression fixture. These IDs and
points illustrate the fixture, not a tested in-game route:

```lua
PickUp = {
    offer = { type = "Item", itemid = 4881 },
    acquire = {
        {
            itemid = 9999,
            type = "KillAndLoot",
            Logic = "Spot",
            WhitelistIDs = { 3192 },
            Points = { { 1, 2, 3, 35 } },
        },
        {
            itemid = 4881,
            type = "InteractWithObject",
            objectid = 3239,
            Logic = "Bounce",
            Points = { { -223.87, -5095.70, 49.97, 5 } },
        },
    },
    Points = {},
},
```

A row's `itemid` means the item to **obtain**, not an item-use instruction. A row
stays completed after that item is observed during this run, even if a later
method consumes it. Open loot pauses acquisition. A missing starter with no
remaining valid method waits and warns. It cannot bypass quest prerequisites.
Acquisition navigation currently does not copy a point's `MapID` into its
temporary route; keep acquisition rows in the current world.

## Custom code

Every phase may attach `customcode(NX, phase, substate)`. It runs on active bot
pulses, including combat, before normal phase handling. Its return value does
not replace or complete a normal action. Keep it bounded and avoid repeating a
side effect every pulse.

A standalone `CustomCode` objective in a full run completes on `true`:

```lua
{
    type = "CustomCode",
    objectiveIndex = 1,
    customcode = function(NX, phase, substate)
        -- Example: allow progression when this phase reaches Active.
        return substate == "Active"
    end,
},
```

If that index belongs to an already finished quest objective, the full runner
skips it. Use `MoveTo` for arrival independent of quest credit. Arrival/custom
completion flags live in memory, not saved checkpoints across a file reload or
`/reload`.

The routine action **Run Quest Phase** handles `CustomCode` differently: with a
quest ID and objective index it waits for live objective credit; without both,
it uses a run-once completion check. That task action does not test the
`_customDone` flag set by a `true` return. Use **Run Full Quest** or direct
profile loading when the function's return must drive progression.

## Capture and check your file

1. In **Profile Tool → Profile → General**, choose `Questing` and enter the
   **Quest ID**. Without a valid ID, export warns and writes normal profile
   format rather than a runnable `Executecodeorder` quest.
2. Add **Quest Steps**. On an NPC/unit step, **Capture Target** fills the ID and
   adds a point at the selected target's position. It adds a point rather than
   replacing all existing points.
3. Open the step's **Pathing Points**. Use **Player Position**,
   **Target Position** or **Mouse Click**, then check X/Y/Z, range and map in
   point detail. Enter object, item, spell and quest IDs in their contextual
   fields; target capture does not discover every kind of ID.
4. Save locally and inspect the Lua for `Executecodeorder`, quest ID, phase
   blocks and points. Load it in **Profiles**, start, and watch the phase and
   quest-log changes described above.

Keep one quest per file and chain them with
[routines](/en/developer/tasks/task-routines). A routine can stop a long-running
phase with a level, time or quest-state condition.

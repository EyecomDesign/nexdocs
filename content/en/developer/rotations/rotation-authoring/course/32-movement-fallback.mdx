# 32. Add a bounded path fallback

One destination can be unwalkable while nearby points are reachable. This
complete Warlock TBC example builds at most 21 candidates: 8, 12 and 16 yards
from the player's starting position, at 0, ±30, ±60 and ±90 degrees from the
direction away from the target. Each candidate keeps the starting height;
only a successful complete router result establishes a usable route.

## Running the example

Save the [Lua file](/rotation-authoring/Bounded_Movement_Example.lua) in your
existing local rotation location and load it as a rotation. Its `Retreat` toggle
is off by default. With a valid enemy target during engagement/combat, turn it
on to try one maneuver. The included Corruption, Curse of Agony and Shadow Bolt
priority continues while a path waits or is followed. Ordinary spell gates can
still hold a hardcast while moving.

Turn `Retreat` off to cancel and rearm it. Before switching or unloading the
rotation, wait for `Bounded movement: cancelled`, `pulse-gap`, `complete` or
another terminal cleanup line. This matters because the public movement
override is global: no public disposal hook or owner token can isolate an old
timer from a newly loaded rotation. If a maneuver already ended, its timer and
ownership have already been cleared. This example teaches the current public
API; broader lifecycle design remains separate from this demonstration.

## Bounds and exits

| Situation | Behavior |
| --- | --- |
| Request pending | One router request remains outstanding; normal combat continues. |
| Failed, empty or partial route / rejected installation | Advance to the next candidate on another pulse, up to 21. |
| Request reaches 5 seconds | End the maneuver and invalidate its generation. |
| Followed route reaches 8 seconds / whole maneuver reaches 20 seconds | End and release movement ownership. |
| Target lost, dead, changed GUID, or moved over 6 yards | Discard the maneuver and queued results. |
| Player dies or moves over 2 yards while waiting | End rather than use a path from an obsolete origin. |
| Pause or another pulse gap over 0.5 seconds | Watchdog ends the maneuver; resume does not install a queued old result. |
| Player reaches within 1.5 yards of the accepted endpoint | End as complete and smoothly face the current target. |

The callback only fills an inbox. A live pulse validates generation, request ID
and current target before installing it. Inline cache callbacks are safe because
the request ticket is stored before the call. Cleanup leaves the old in-flight
slot occupied until its callback settles, so toggling on again cannot overlap
that physical request. There is no public cancellation function for standalone
`RequestPath`; if it never settles, end/reload the demo instead of queuing more.
The numeric result `status` and failure `reason` are retained in terminal
diagnostics; `pending`, `ready` and `following` here are the example's local
states, not new NX API status values.

The watchdog uses the game's `C_Timer.NewTicker`, and deadlines use `GetTime()`.
Timers are not script event listeners: this file cancels its own timer in every
terminal path. Pulse loss is a conservative pause detector, not a public paused
state query, and can also end a maneuver during another long pulse gap. The
endpoint tolerance is an author choice, not a router completion event.
